────────────────────────────────────────────────────────────────────────────────
THE RESEARCH QUESTION
────────────────────────────────────────────────────────────────────────────────

Next.js serializes server-fetched data into the HTML it sends to the browser so
that React can "hydrate" (reactivate) the page on the client without re-fetching.
This is a performance feature, but it creates a security risk: if a developer
fetches a full database object on the server and passes it as props, every field
in that object — including credentials — is embedded in the raw HTML and readable
by anyone who views the page source. No authentication required. No network
interception needed. Just Ctrl+U.


────────────────────────────────────────────────────────────────────────────────
WHAT WAS BUILT
────────────────────────────────────────────────────────────────────────────────

PHASE 1 — Vulnerable PoC (vulnerable-nextjs-poc/)
──────────────────────────────────────────────────

A Next.js 16 application running both routing paradigms simultaneously, each
with an intentionally vulnerable page.

Mock database (src/db/users.json) — 3 users, each with:

  Field                 Example value
  ──────────────────    ──────────────────────────────────────────
  password_hash         $2b$12$EixZaYVK1fsbw1ZfbX3OXe... (bcrypt)
  two_factor_secret     JBSWY3DPEHPK3PXP (Base32 TOTP seed)
  api_key               sk_live_1234567890abcdef
  ssn                   000-00-0001
  name, email, role,    Public-safe fields
  created_at


/vulnerable-pages — Pages Router vulnerability
  File: src/pages/vulnerable-pages.tsx

  getServerSideProps fetches all users from the DB and returns the raw objects
  as props. Next.js automatically serializes these into the __NEXT_DATA__ JSON
  blob embedded in a <script> tag at the bottom of every HTML response. The page
  UI only displays name, email, and role — but the full object including all
  credentials sits in the HTML. The attack is trivial:
  view-source:http://localhost:3001/vulnerable-pages → search for password_hash.


/vulnerable — App Router vulnerability
  Files: src/app/vulnerable/page.tsx + UserListClient.tsx

  A Server Component fetches all users and passes the raw User[] array directly
  as a prop to a 'use client' Client Component. The moment data crosses the
  Server→Client component boundary, Next.js serializes it into the RSC (React
  Server Component) payload — a series of self.__next_f.push([...]) inline script
  chunks. Again the UI only shows name and email, but every credential travels
  across the wire.


PHASE 2 — Automated Scanner (nextjs-hydration-scanner/)
────────────────────────────────────────────────────────

A Python scanner (scanner.py) that automates the attack a researcher or attacker
would perform manually.

How it works:
  1. Fetches the target URL's HTML via requests
  2. Channel 1 — Pages Router: Finds <script id="__NEXT_DATA__">, parses its JSON
  3. Channel 2 — App Router: Finds all self.__next_f.push([...]) chunks, decodes
     the RSC line-delimited format, parses each JSON object
  4. Recursively walks every node in both data trees
  5. At each key, checks two things:
       a. Does the field name match a sensitive pattern?
          (e.g. /password/i, /api_key/i, /ssn/i, /secret/i)
       b. Does the field value match a known secret format?
          (bcrypt regex, sk_live_ prefix, SSN format, Base32, JWT, AWS key)
  6. Assigns CRITICAL / HIGH / MEDIUM severity and emits a structured report
  7. Auto-saves every run to findings/ as a timestamped JSON file and updates
     findings/index.json

Sensitive patterns covered:

  Severity    Field name patterns                        Value patterns
  ─────────   ────────────────────────────────────────   ───────────────────────────────────────
  CRITICAL    password, password_hash, api_key, secret,  Bcrypt hash, sk_live_*, SSN format,
              ssn, private_key, two_factor_secret,        GitHub PAT, AWS access key ID
              credit_card
  HIGH        token, access_token, refresh_token, jwt,   JWT, Base32 string, 16-digit card number
              bearer, signing_key
  MEDIUM      admin, is_admin, webhook_secret,           —
              stripe_customer


PHASE 3 — DTO Mitigation (src/lib/dto.ts + secure routes)
──────────────────────────────────────────────────────────

src/lib/dto.ts — the allowlist layer

  export interface PublicUser {
    id:         number;
    name:       string;
    email:      string;
    role:       string;
    created_at: string;
    // NO password_hash, NO api_key, NO ssn, NO two_factor_secret
  }

  export function toPublicUser(user: User): PublicUser { ... }
  export function toPublicUsers(users: User[]): PublicUser[] { ... }

The key design choice is ALLOWLIST over BLOCKLIST. A blocklist
(delete user.password_hash) fails open — a new sensitive DB column is silently
leaked until someone updates the blocklist. An allowlist fails closed — new fields
are invisible to the client until explicitly added to the DTO.

/secure-pages — same getServerSideProps pattern, but calls toPublicUsers() before
  returning props. Only PublicUser shapes enter the __NEXT_DATA__ serialization
  pipeline.

/secure — same Server Component pattern, but calls toPublicUsers() before passing
  data to the Client Component. Only PublicUser shapes cross the RSC boundary.

TypeScript enforcement is a secondary benefit: user.password_hash does not exist
on PublicUser, so any accidental reference to it in client code is a compile
error, not a runtime leak.

Scanner false positives — a documented limitation

  The HIGH-severity findings on the secure routes are all false positives, which
  fall into two categories:

  1. Base32 value pattern — short uppercase strings like "user", "admin", "flex",
     "center", "en" all match the Base32 alphabet regex. These are React internal
     values (CSS classes, HTML attributes, component metadata) that happen to use
     only A–Z and 2–7 characters. Not actual TOTP secrets.

  2. className field name matching /ssn/i — the field name "className" contains
     the substring "ssN" (case-insensitive), which triggers the SSN pattern. The
     values are Tailwind CSS strings like "p-8 font-sans" and Geist font class
     names. Not actual SSN data.

  Both categories are structurally distinguishable from real findings (the paths
  contain className, lang, rel, style, parallelRouterKey — known React/Next.js
  internals) and would be filtered in a production-grade scanner by a
  post-processing allowlist of internal RSC field names.
