\begin{abstract}
Next.js and similar full-stack frameworks gain their performance edge
through server-side pre-rendering followed by client-side
\emph{hydration}.  The mechanics are well understood: the server
serializes data into the HTML response so the browser can reconstruct
React's component tree without a second network round-trip.  What is
considerably less obvious is the security consequence.  When developers
return raw database records as component props---a widespread and
seemingly harmless pattern---every field in those records, including
password hashes, API keys, Social Security Numbers, and two-factor
authentication secrets, is silently embedded in plain-text HTML and
delivered to every requesting client, authenticated or not.  The
vulnerability manifests across both the legacy Pages Router (through
the \texttt{\_\_NEXT\_DATA\_\_} script tag) and the modern App Router
(through React Server Component streaming payloads).  We present three
artifacts: an intentionally vulnerable proof-of-concept application, an
automated Python scanner that detects exposure across both serialization
channels, and a Data Transfer Object (DTO) mitigation that eliminated
100\% of confirmed critical findings in our experiments.  The scanner
identified 24 critical credential exposures across two route
implementations.  After applying the DTO pattern, zero critical findings
remained.  Explicit, allowlist-based data stripping at the
server--client boundary is not optional good practice.  It is a
security requirement.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Server-Side Rendering (SSR) is no longer a niche technique.  Since
React-based meta-frameworks like Next.js, Nuxt, and SvelteKit went
mainstream, SSR has become the default architecture for production web
applications---valued for its effect on perceived load time and
search-engine discoverability~\cite{next16docs}.  The model is
conceptually simple: the server generates a complete HTML page and
streams it to the browser, which then takes over rendering
responsibilities.

Taking over requires data.  The client-side JavaScript runtime must
receive exactly the data the server used to render the page, or React's
reconciliation algorithm cannot hydrate the component tree without an
additional network fetch.  In practice, this means the data is
serialized directly into the HTML response as a JSON payload.  The
design is intentional---and, under certain conditions, it constitutes a
serious security hazard: \emph{every field in every object passed from
server to client component is publicly readable in the HTML source.}

The hazard is easy to miss.  A developer looks at a component that
displays a user's name and email.  The component works correctly.
Nothing appears wrong.  What that developer may not consider is that
the entire \texttt{User} object---including its \texttt{password\_hash},
\texttt{api\_key}, and \texttt{ssn} fields---was serialized into the
response alongside the fields the component actually renders.  No
development tool raises a warning.  No browser security policy
intervenes.  The data is simply there, in plaintext, in the page
source, retrievable by any person or automated script that issues an
HTTP request.

This paper makes the following contributions:

\begin{itemize}
  \item A systematic analysis of the two distinct serialization channels
        in Next.js through which sensitive data leaks
        (Section~\ref{sec:background}).
  \item An intentionally vulnerable proof-of-concept application
        demonstrating the attack on both the Pages Router and the App
        Router (Section~\ref{sec:methodology}).
  \item An open-source automated scanner that detects hydration leakage
        across both channels using field-name and value-pattern heuristics
        (Section~\ref{sec:methodology}).
  \item A Data Transfer Object mitigation strategy, its implementation,
        and empirical validation via scanner-confirmed zero findings
        (Section~\ref{sec:mitigation}).
  \item A discussion of scanner limitations, false positives, and
        directions for future tooling (Section~\ref{sec:discussion}).
\end{itemize}

All artefacts---the vulnerable and mitigated Next.js application, the
Python scanner, all scan reports, and the source for this paper---are
available at \url{[Link redacted for double-blind review]}.

\section{Background and Related Work}
\label{sec:background}

\subsection{Server-Side Rendering and Hydration}

Next.js exposes two rendering models relevant to this work.  In the
\emph{Pages Router}---the older paradigm---each page exports a
\texttt{getServerSideProps} function that runs on the server for every
incoming request, fetches data, and returns a plain JavaScript object.
Next.js passes that object as props to the React component and,
critically, serializes the entire \texttt{props} tree into a JSON blob
embedded in a \texttt{<script>} tag bearing
\texttt{id="\_\_NEXT\_DATA\_\_"}~\cite{next16docs}.  That tag is
transmitted to every client, regardless of authentication state.

The \emph{App Router}, introduced in Next.js 13 and stabilised in
version 14+, works differently.  It uses React Server
Components (RSC)~\cite{rsc2023}.  Server Components run exclusively on
the server and can fetch data directly, but when one passes props to a
\texttt{'use client'} Client Component those props must cross the
server--client serialization boundary.  The RSC protocol encodes that
data as a stream of \texttt{self.\_\_next\_f.push([type, payload])}
inline script calls, where the payload carries newline-delimited,
JSON-encoded React tree segments.

In both models, the mechanism is \emph{necessary} for correct
hydration.  It is equally \emph{dangerous} when the objects crossing
the boundary contain fields that were never intended for client
consumption.

\subsection{Relationship to Existing Vulnerability Classes}

Hydration leakage does not fit neatly into classical vulnerability
categories, and that is part of what makes it easy to overlook.  Unlike
Cross-Site Scripting (XSS)~\cite{owasp_xss}, no content injection is
involved---the server is the source.  Unlike SQL
injection~\cite{owasp_sqli}, the query is well-formed and the
application logic is otherwise correct.  Unlike information disclosure
through verbose error messages~\cite{cwe200}, the exposure is not a
failure mode.  It is a side-effect of a perfectly successful request.

Standard defences offer no relief.  Content Security Policy headers,
the canonical XSS mitigation, do nothing here: the leaking data is
first-party, server-rendered JSON, not injected script~\cite{csp_mdn}.
HTTPS prevents interception in transit, but the exposure sits at the
\emph{origin}---any browser request, authenticated or not, retrieves
the data.  Rate limiting and bot detection can slow bulk enumeration.
They cannot stop a single manual page view from exposing every
serialized record.

\subsection{Prior Work}

Practitioners first raised concerns about Next.js data exposure in blog
posts around 2021--2022, in the wake of
\texttt{getServerSideProps}~\cite{nwh2022}.  Netanel
Basal~\cite{basal2022} and the official Next.js security
documentation~\cite{next_security} both caution that return values from
\texttt{getServerSideProps} are visible to clients, but neither provides
automated detection tooling.

Academic coverage of framework-specific serialization risk remains
sparse.  Luo et al.~\cite{luo2023} examine state exposure in SPAs via
Redux DevTools, which requires browser extension access.  The work
presented here targets network-layer exposure: no extension required,
no special tooling---just an HTTP client.  It also covers both the
legacy and modern Next.js routing paradigms, which prior work does not.

The OWASP API Security Top 10~\cite{owasp_api2023} identifies
\emph{Excessive Data Exposure} (API3:2023) as a top-tier risk, defined
as APIs returning more data than the client needs and relying on the
client to filter.  Our findings are a concrete instantiation of this
risk class, grounded in the SSR hydration context.

\section{Methodology}
\label{sec:methodology}

The methodology has two parts.  The first is a purpose-built vulnerable
application that faithfully reproduces the class of developer mistakes
that trigger hydration leakage.  The second is an automated scanner
designed to detect the resulting exposure.

\subsection{Phase 1: Vulnerable Proof-of-Concept Application}

running on a local development server.  A mock user database lives in

\subsubsection{Vulnerability 1: Pages Router (\texttt{\_\_NEXT\_DATA\_\_})}

The Pages Router page at \texttt{/vulnerable-pages} exports
\texttt{getServerSideProps}, which fetches the full user list and
returns it as the \texttt{users} prop.  The React component renders
only name, email, and role.  Listing~\ref{lst:vuln_pages} shows the
vulnerable pattern.

\begin{lstlisting}[style=typescript, caption={Vulnerable Pages Router: raw
  database objects returned as props.}, label={lst:vuln_pages}]
// src/pages/vulnerable-pages.tsx
export const getServerSideProps: GetServerSideProps<Props> = async () => {
  const users = await getUsers(); // returns full User[] from DB

  // VULNERABILITY: raw DB objects returned directly.
  // Next.js serializes ALL fields into __NEXT_DATA__ in the HTML.
  return { props: { users } };
};
\end{lstlisting}

The resulting HTML contains the embedded JSON shown in
Listing~\ref{lst:next_data}.  Every field---the bcrypt hash, TOTP seed,
API key, and SSN---appears verbatim in the page source, reachable by
any HTTP request.

\begin{lstlisting}[style=json, caption={Excerpt of \_\_NEXT\_DATA\_\_ in
  the HTML response, showing leaked credentials.}, label={lst:next_data}]
<script id="__NEXT_DATA__" type="application/json">

        "id": 1,

        "password_hash": "$2b$12$EixZaYVK1fsbw1ZfbX3OXe...",

</script>

\subsubsection{Vulnerability 2: App Router (RSC Payload)}

The App Router page at \texttt{/vulnerable} is a Server Component that
fetches users and passes the raw array to a \texttt{'use client'}
Client Component.  Listing~\ref{lst:vuln_app} shows the Server
Component.

\begin{lstlisting}[style=typescript, caption={Vulnerable App Router:
  raw objects crossing the RSC serialization boundary.},
  label={lst:vuln_app}]
// src/app/vulnerable/page.tsx
export default async function VulnerableAppRouterPage() {
  const users = await getUsers(); // full User[] from DB

  // VULNERABILITY: entire User[] passed to Client Component.
  // Next.js encodes all fields into self.__next_f.push() payloads.
  return <UserListClient users={users} />;
}
\end{lstlisting}

\texttt{UserListClient} renders only \texttt{user.name} and
\texttt{user.email}.  That restraint is irrelevant.  The entire
\texttt{User} object---\texttt{password\_hash}, \texttt{api\_key},
\texttt{ssn}, \texttt{two\_factor\_secret} and all---is serialized into
the RSC streaming payload embedded in the initial HTML response.

The RSC protocol fragments this data across consecutive
\texttt{self.\_\_next\_f.push([type, data])} calls, with row type 1
carrying JSON-encoded component tree segments.  Unlike the monolithic
\texttt{\_\_NEXT\_DATA\_\_} blob, the RSC payload is spread across many
such calls and requires parsing a newline-delimited format where each
line takes the form \texttt{<row\_id>:<json\_value>}.

\subsection{Phase 2: Automated Vulnerability Scanner}

We implemented a Python 3.12 scanner---\texttt{scanner.py},
approximately 310 lines---to automate detection of hydration leakage.
It uses \texttt{requests} for HTTP fetching and \texttt{BeautifulSoup}
for HTML parsing.

\subsubsection{Extraction Pipeline}

The scanner handles both Next.js serialization channels through
separate extraction paths:

\begin{enumerate}
  \item \textbf{Pages Router}: BeautifulSoup locates the
        \texttt{<script id="\_\_NEXT\_DATA\_\_">} tag and parses its
        \texttt{string} attribute as JSON.

  \item \textbf{App Router}: A compiled regular expression
        \texttt{r'self\textbackslash .\_\_next\_f\textbackslash
        .push\textbackslash(\textbackslash s*(\textbackslash[
        \textbackslash s\textbackslash S]*?\textbackslash])\textbackslash
        s*\textbackslash)'} locates all RSC push calls in the HTML.
        Each matched payload is parsed, the row type inspected, and
        row-type-1 payloads further split by newline and parsed as
        individual JSON objects.  All recovered objects are collected
        into a list for further analysis.
\end{enumerate}

\subsubsection{Recursive Tree Walker}

Once JSON data is recovered from either channel, the scanner walks the
Python object graph recursively.  At each dictionary key, two
independent checks run:

\begin{enumerate}
  \item \textbf{Field-name pattern matching}: The key is tested against
        29 compiled regular expressions organised into three severity
        tiers.  Patterns are ordered from most specific to most
        general---\texttt{password\_hash} before \texttt{password},
        for instance---so the most descriptive label is assigned when
        a key matches multiple patterns.  The first match wins; a
        \texttt{set} of already-flagged paths is maintained across the
        recursion to prevent duplicate findings.

  \item \textbf{Value pattern matching}: If a field was not flagged by
        a name pattern and its value is a string, that value is tested
        against eight compiled format-pattern regular expressions
        covering bcrypt hashes, Stripe-format API keys, SSN format,
        JWTs, GitHub personal access tokens, AWS access key IDs,
        Base32 strings (potential TOTP secrets), and 13--16-digit
        numeric sequences (potential credit card numbers).
\end{enumerate}

\section{Mitigation: The Data Transfer Object Pattern}
\label{sec:mitigation}

\subsection{Design Rationale}

Hydration leakage stems from a missing boundary.  The server's internal
data representation---a full database record---reaches the client
unchanged because nothing compels a developer to distinguish between
``data I fetched'' and ``data the client is permitted to see.''  Two
strategies can enforce that distinction:

\begin{enumerate}
  \item \textbf{Blocklist (field deletion)}: After fetching, explicitly
        delete sensitive fields before returning props, e.g.,
        \texttt{delete user.password\_hash}.

  \item \textbf{Allowlist (DTO projection)}: Define a separate type
        containing only the fields permitted to cross the boundary, and
        construct instances of that type from the database records.
\end{enumerate}

The \emph{allowlist} approach is the right choice.  A blocklist is
\emph{open by default}---add a sensitive column to the database schema
and it leaks to clients until someone remembers to patch the deletion
list.  An allowlist is \emph{closed by default}---new fields simply do
not exist from the client's perspective until deliberately added to the
DTO.  The TypeScript type system can enforce this at compile time,
making a violation a build error rather than a silent runtime leak.

\subsection{Implementation}

A \texttt{PublicUser} DTO interface was defined in
\texttt{src/lib/dto.ts}, holding only the five fields appropriate for
client consumption.  Listing~\ref{lst:dto} shows the full
implementation.

\begin{lstlisting}[style=typescript, caption={DTO definition and
  transformation function in \texttt{src/lib/dto.ts}.},
  label={lst:dto}]
export interface PublicUser {
  id:         number;
  name:       string;
  email:      string;
  role:       string;
  created_at: string;
  // password_hash, api_key, ssn, two_factor_secret: absent.
}

export function toPublicUser(user: User): PublicUser {
  return {
    id:         user.id,
    name:       user.name,
    email:      user.email,
    role:       user.role,
    created_at: user.created_at,
  };
}

export const toPublicUsers = (users: User[]): PublicUser[] =>
  users.map(toPublicUser);
\end{lstlisting}

The explicit destructuring inside \texttt{toPublicUser} is
load-bearing.  TypeScript's structural type check ensures that any
field absent from the return literal is excluded from the output type.
Client Components that accept \texttt{PublicUser[]} rather than
\texttt{User[]} gain a further safety layer: referencing
\texttt{user.password\_hash} inside client code is a compile-time type
error, not a runtime leak.

\subsubsection{Pages Router Integration}

The secure Pages Router page, \texttt{/secure-pages}, wraps the
database result with \texttt{toPublicUsers} before returning props:

\begin{lstlisting}[style=typescript, caption={DTO-secured
  \texttt{getServerSideProps}.}, label={lst:secure_pages}]
export const getServerSideProps: GetServerSideProps<Props> =
  async () => {
    const users = await getUsers();
    return { props: { users: toPublicUsers(users) } };
  };
\end{lstlisting}

Only the \texttt{PublicUser} shape enters the
\texttt{\_\_NEXT\_DATA\_\_} serialization pipeline.

\subsubsection{App Router Integration}

The secure App Router Server Component, \texttt{/secure}, applies the
transformation before handing data to the Client Component:

\begin{lstlisting}[style=typescript, caption={DTO-secured
  App Router Server Component.}, label={lst:secure_app}]
export default async function SecureAppRouterPage() {
  const users      = await getUsers();
  const publicUsers = toPublicUsers(users); // strip before boundary

  return <SecureUserListClient users={publicUsers} />;
}
\end{lstlisting}

The RSC boundary only ever sees \texttt{PublicUser} objects.  Sensitive
fields are gone before \texttt{self.\_\_next\_f.push} encodes anything.

\section{Discussion and Limitations}
\label{sec:discussion}

\subsection{False Positives in the Scanner}

The scanner flagged HIGH-severity findings on every scanned route,
including the mitigated ones.  All of them are false positives.  They
arise from two structural properties of the Next.js payload format.

\subsubsection{Base32 Value Pattern}

The TOTP secret heuristic matches
\texttt{\textasciicircum[A-Z2-7]+=*\$}---any string drawn entirely from
the Base32 alphabet.  Short React-internal strings satisfy this
trivially: \texttt{``user''}, \texttt{``admin''}, \texttt{``flex''},
\texttt{``center''}, \texttt{``en''} (the HTML \texttt{lang}
attribute), and \texttt{``development''} (the Next.js \texttt{buildId})
all match.  None of them are TOTP secrets.  They are component tree
metadata, HTML attributes, and CSS class names.

\subsubsection{Field Name Substring Matching: \texttt{className}}

React serializes component props into JSON, \texttt{className}
included.  The field name \texttt{className} contains the substring
\texttt{ssN} case-insensitively, which triggers the SSN field-name
pattern.  The associated values are Tailwind CSS utility strings---
\texttt{``p-8 font-sans''}, Geist font identifiers---not Social
Security Numbers.

\subsubsection{Mitigating False Positives}

Both false positive classes share a structural tell: they appear at
paths containing well-known React-internal field names
(\texttt{className}, \texttt{lang}, \texttt{rel},
\texttt{parallelRouterKey}, \texttt{style.*}), and they appear on
mitigated and vulnerable routes alike.  A production-grade scanner
could suppress them through an allowlist of internal RSC field names or
a minimum-length guard on value matches.  We leave that refinement to
future work.

The false positive rate on genuine user-data paths is \textbf{zero}.
Every CRITICAL finding that references a user array path (e.g.,
\texttt{users[0].password\_hash}) was a confirmed true positive.

\subsection{Scope and Generalizability}

The mock database used here is a local JSON file---simpler than
production.  Real Next.js applications typically use ORMs such as
Prisma~\cite{prisma} against relational or document databases.  Those
ORMs return typed model objects that often carry \emph{more} fields
than the minimal schema used here.  The hydration leakage mechanism is
unchanged; if anything, ORMs raise the risk by making over-fetching
the path of least resistance.

The vulnerability is not Next.js-specific.  Any SSR framework that
serializes server-fetched data into the HTML response and passes it to
client-side components---Nuxt 3 (Vue), SvelteKit, Remix, and Astro in
hybrid mode---is susceptible to the same class of exposure when
developers pass raw database records across the server--client boundary.
The DTO pattern described here is entirely framework-agnostic.

\subsection{Developer Tooling Gap}

No existing build-time or lint-time tool warns when a
\texttt{getServerSideProps} return value or Server Component prop
carries fields never declared as safe for the client.  TypeScript's
structural type system sees no difference between a database record
interface and a DTO interface; without nominal typing or explicit
boundary annotations, the compiler allows the leak through silently.

An ESLint plugin that enforces DTO use at \texttt{getServerSideProps}
return sites and at RSC-to-Client-Component prop boundaries would close
this gap.  We identify that as the most direct direction for follow-on
work.

\section{Conclusion}
\label{sec:conclusion}

The hydration mechanism in Next.js---shared by both the Pages Router
and the App Router---is a latent information-disclosure vulnerability
when developers pass raw database records as component props.  The
exposure asks nothing of an attacker.  No elevated privilege.  No
network interception.  No browser extension.  The data sits in the
plain-text HTML of every response, waiting.

Our scanner confirmed 24 CRITICAL credential exposures across two
route implementations: bcrypt password hashes, live API keys, Social
Security Numbers, and TOTP two-factor seeds.  All 24 vanished after
applying the Data Transfer Object mitigation.  The fix required 22
lines of TypeScript.

Three practices follow from this work:

\begin{enumerate}
  \item \textbf{Adopt the DTO allowlist pattern universally.} Every
        data access in \texttt{getServerSideProps} and every prop
        passed from a Server Component to a Client Component should be
        projected through an explicit DTO before crossing the boundary.

  \item \textbf{Treat the serialized HTML payload as a public API
        surface.} Any field inappropriate in a REST response to an
        unauthenticated caller is equally inappropriate in the
        hydration payload.

  \item \textbf{Include hydration payload review in security audits.}
        Existing scanning tools focus on XSS, injection, and
        authentication bypasses.  Automated checks against
        \texttt{\_\_NEXT\_DATA\_\_} and RSC push payloads should be
        added to standard web-application security assessment
        methodology.
\end{enumerate}

SSR frameworks are the default now, and they will remain so.  As that
architectural dominance deepens, the boundary between server-side data
and client-side rendering must receive the same security scrutiny
historically applied to API design---because in a hydrated application,
that boundary \emph{is} the API.
