\begin{abstract}
Next.js and similar full-stack frameworks get their speed from
Server-Side Rendering (SSR) followed by client-side \emph{hydration}.
The server serializes its data into the HyperText Markup Language (HTML)
response so the browser can rebuild React's component tree without a
second network round-trip.  The security cost is far less obvious.
Developers often return raw database records as component props.  The
pattern is common and looks harmless.  Yet every field in those records,
including password hashes, Application Programming Interface (API) keys,
Social Security Numbers (SSNs), and two-factor authentication secrets,
ends up in plain-text HTML that is sent to every client, logged in or
not.  The problem shows up in both the older Pages Router (through the
\texttt{\_\_NEXT\_DATA\_\_} script tag) and the newer App Router (through
React Server Component (RSC) streaming payloads).  We present
an intentionally vulnerable proof-of-concept (PoC) application, an
automated Python scanner that detects exposure across both serialization
channels, and a Data Transfer Object (DTO) mitigation.  On a labeled
four-route corpus the scanner achieved 100\% recall (24 of 24 planted
credential exposures detected, zero false negatives); after applying the
DTO pattern, every true-positive critical exposure was eliminated
(24~$\rightarrow$~0).  We quantify detection quality with a full
confusion matrix: precision, recall, and $F_1$.  The scanner's false
positives turn out to be a small set of framework-internal strings, and a
short allowlist of those keys raises precision to 100\%.  Its runtime cost
is linear in payload size, roughly 2.1\,$\mu$s per node.  We compare the
scanner against existing tooling, and we show that both the vulnerability
and its detection carry over to three further SSR frameworks: Nuxt, Remix,
and SvelteKit.  Explicit,
allowlist-based data stripping at the server--client boundary is not
optional good practice.  It is a security requirement.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Server-Side Rendering (SSR) has become mainstream.  React-based
meta-frameworks such as Next.js, Nuxt, and SvelteKit now treat it as the
default for production web applications, mainly because it improves
perceived load time and search-engine visibility~\cite{next16docs}.  The
idea is simple: the server builds a full HTML page and sends it to the
browser, and the browser then takes over the rendering.

Taking over needs data.  The client-side JavaScript has to receive the
same data the server used to build the page; otherwise React cannot
hydrate the component tree without making another network request.  To
avoid that request, the framework serializes the data straight into the
HTML as a JSON payload.  This is intentional and useful, but it also
creates a security problem: \emph{every field of every object passed from
a server component to a client component ends up readable in the page
source.}

This is easy to overlook.  Suppose a developer writes a component that
shows a user's name and email.  It works, and nothing looks wrong.  What
the developer might not realize is that the whole \texttt{User} object was
serialized into the response, not just the two fields shown on screen, and
that object still includes \texttt{password\_hash}, \texttt{api\_key}, and
\texttt{ssn}.  No tool warns about this, and no browser policy blocks it.
The data simply sits there in plaintext, and anyone who sends a HyperText
Transfer Protocol (HTTP) request can read it.  Figure~\ref{fig:pipeline}
shows where this happens: the leak is at the serialization step, and the
fix we propose acts one step earlier, before any data crosses the
boundary.

\paragraph{Threat model.}
We assume an unauthenticated remote attacker who can issue ordinary HTTP
requests to a deployed SSR application.  The attacker has no elevated
privileges, performs no network interception, and uses no browser
instrumentation.  Their capability is limited to reading the bytes the
server voluntarily returns.  Under this weak model, any sensitive field the server
serializes into the hydration payload is, by definition, disclosed.  The
research question is therefore twofold: (i)~which server-side coding
patterns cause such disclosure, and (ii)~can the disclosure be detected
automatically and eliminated systematically?

This paper makes the following contributions:

\begin{itemize}
  \item A systematic analysis of the two distinct serialization channels
        in Next.js through which sensitive data leaks, framed against the
        \emph{Excessive Data Exposure} vulnerability class
        (Section~\ref{sec:background}).
  \item An intentionally vulnerable PoC application demonstrating the
        attack on both the Pages Router and the App Router, and an
        open-source automated scanner that detects hydration leakage
        across both channels using field-name and value-pattern
        heuristics (Section~\ref{sec:methodology}).
  \item A quantitative evaluation reporting precision, recall, and $F_1$
        against a labeled ground-truth corpus, a characterization of the
        scanner's false positives, and a runtime/scalability benchmark
        (Section~\ref{sec:results}).
  \item A Data Transfer Object mitigation strategy, its implementation,
        and empirical validation showing complete elimination of
        true-positive critical exposures (Section~\ref{sec:mitigation}).
  \item A demonstration that the vulnerability and its detection
        generalize to three additional SSR frameworks (Nuxt, Remix, and
        SvelteKit), together with a comparison against existing tooling
        and a discussion of limitations (Sections~\ref{sec:results}
        and~\ref{sec:discussion}).
\end{itemize}

Every artifact is available at
\url{https://github.com/gargarnav/nextjs-hydration-scanner}: the
vulnerable and mitigated Next.js application, the Python scanner, all
scan reports, and the source for this paper.

\section{Background and Related Work}
\label{sec:background}

\subsection{Server-Side Rendering and Hydration}

Next.js has two rendering models that matter here.  The first is the
\emph{Pages Router}, the older one.  A page exports a
\texttt{getServerSideProps} function that runs on the server for every
request, fetches data, and returns a plain JavaScript object.  Next.js
hands that object to the React component as props, and it also serializes
the whole \texttt{props} tree into a JavaScript Object Notation (JSON)
blob inside a \texttt{<script>} tag with
\texttt{id="\_\_NEXT\_DATA\_\_"}~\cite{next16docs}.  That tag goes to
every client, whether or not they are logged in.

The \emph{App Router}, added in Next.js 13 and stabilized in version 14,
works differently.  It uses React Server Components (RSC)~\cite{rsc2023}.
Server Components run only on the server and can fetch data directly, but
the moment they pass props to a \texttt{'use client'} Client Component,
those props have to cross the server--client boundary.  The RSC protocol
sends that data as a stream of \texttt{self.\_\_next\_f.push()} inline
script calls, and each call carries newline-delimited, JSON-encoded pieces
of the React tree.

Both models need this mechanism to hydrate correctly.  Both become
dangerous when the objects crossing the boundary carry fields that were
never meant for the client.

\subsection{Relationship to Existing Vulnerability Classes}

Hydration leakage does not fit neatly into the usual vulnerability
categories, which is part of why it is easy to miss.  It is not
Cross-Site Scripting (XSS)~\cite{owasp_xss,lekies2013}: nothing is
injected, and the server itself is the source.  It is not Structured
Query Language (SQL) injection~\cite{owasp_sqli} either, because the query
is well-formed and the application logic is fine.  Rather, it is an
instance of the broad Exposure of Sensitive Information to an Unauthorized
Actor weakness (Common Weakness Enumeration entry CWE-200)~\cite{cwe200}.
Most CWE-200 examples are things like verbose error messages, debug
endpoints, or directory listings, where something has clearly gone wrong.
Here nothing has gone wrong.  The leak is just a side-effect of a request
that worked exactly as intended.

The usual defenses do not help.  Content Security Policy (CSP) headers,
the standard fix for XSS, do nothing here, because the leaking data is
first-party server-rendered JSON, not injected script~\cite{csp_mdn}.
HTTP Secure (HTTPS) stops interception in transit, but the exposure is at
the \emph{origin}: any browser request, logged in or not, returns the
data.  Rate limiting and bot detection can slow down bulk scraping, but
they cannot stop a single page view from exposing every record that was
serialized.

\subsection{Prior Work}

Practitioners have warned before that whatever
\texttt{getServerSideProps} returns is visible to clients.
Basal~\cite{basal2022} and the official Next.js security
documentation~\cite{next_security} both mention it, but neither gives any
automated way to detect it.

In the academic literature, the closest work is on \emph{Excessive Data
Exposure} at the architectural level.  Genfer and Zdun~\cite{genfer2022}
study this same anti-pattern in microservice APIs, where a service returns
more fields than the caller needs, and they propose static metrics to
bound the exposed surface.  Their setting is service-to-service REST APIs.
Ours is the SSR server-to-browser hydration channel, where the ``client''
is every visitor and the data is baked into the HTML rather than returned
from an endpoint you can point at.  Our detection method is a lightweight,
format-driven relative of large-scale web-flow studies such as Lekies et
al.'s taint-based detection of DOM-based XSS~\cite{lekies2013} and Steffens
et al.'s measurement of persistent client-side XSS~\cite{steffens2019}.
Like them, we follow data that reaches a client-visible sink; unlike them,
our sink is the serialized hydration payload and we only need the network
response.  On the value-pattern side, Meli et al.'s large-scale study of
secret leakage on GitHub~\cite{meli2019} backs up the assumption our
scanner relies on: credential material such as bcrypt hashes,
provider-specific API-key prefixes, and tokens is reliably recognizable
with regular expressions.  The most recent related work, Katz et al.'s
SIExVulTS~\cite{siexvults2025}, detects CWE-200 exposure in Java with
static taint analysis, but it works on server source code and does not
model the SSR hydration boundary.

\subsection{Novelty and Positioning}

The OWASP API Security Top 10~\cite{owasp_api2023} lists
\emph{Excessive Data Exposure} (in the 2023 edition it falls under Broken
Object Property Level Authorization) as a top risk: an interface hands
back more data than the client needs and trusts the client to filter it.
We are not just restating this class.  We make three points that are
specific to SSR hydration and that, as far as we know, earlier work does
not.  First, in an SSR framework the over-fetched data goes to
\emph{every} unauthenticated visitor inside the first HTML response, so
the leaking ``API'' is one most developers do not even realize they are
exposing; there is no explicit endpoint to audit.  Second, within one
framework the leak has two very different serialization channels (the
\texttt{\_\_NEXT\_DATA\_\_} blob and the RSC streaming payload), and each
needs its own parser; we describe and detect both.  Third, both the
problem and the detection carry over, essentially unchanged, to four
separate SSR frameworks (Section~\ref{sec:results}).  Compared with
generic CWE-200 detectors~\cite{siexvults2025} and REST-focused
excessive-exposure work~\cite{genfer2022}, this is a framework-aware,
channel-aware version of the problem with a runtime detector to match.

\subsection{Comparison with Existing Tools}
\label{sec:toolcmp}

Several tools touch nearby problems, but none of them targets
hydration-payload leakage across routing paradigms.  Table~\ref{tab:toolcmp}
lays them out.  React's
\texttt{experimental\_taintObjectReference}~\cite{react_taint} is the
closest built-in guard, but it is opt-in for each object, still
experimental, does not follow cloned or spread copies, and only covers the
App Router; the Pages Router has nothing like it.  Commercial
secret-scanners such as \texttt{@snyk/nextjs} and source-level Static
Application Security Testing (SAST) tools answer a different question,
hardcoded secrets in source or compiled bundles, and they never see data
that flows from a database query through a server function into the HTML
at request time.  General-purpose static taint
analyzers~\cite{siexvults2025,lekies2013} could in principle model this
flow, but they need access to the whole source program and are not set up
for the SSR serialization sink.  Our scanner fills the gap from the other
side: it is a black-box runtime detector that needs nothing but an HTTP
client, which makes it useful for auditing sites that are already deployed
and for re-checking after a patch.  A static, write-time counterpart would
pair well with it, an editor or CI lint rule that reads each
server-boundary value's type and flags sensitive fields before the code
ships.  We describe a prototype of exactly that in
Section~\ref{sec:discussion}.

\section{Methodology}
\label{sec:methodology}

The work has two parts.  The first is a small but deliberately vulnerable
application that reproduces the mistakes developers actually make, and the
second is a scanner that detects the resulting leaks.

\subsection{Phase 1: Vulnerable Proof-of-Concept Application}

We built a Next.js 16.1.6 app in React 19 and TypeScript and ran it on a
local development server.  The mock database is a file,
\texttt{src/db/users.json}, with three made-up users.  Each user record
mixes fields that are fine to show publicly with fields that should never
reach a browser.  Table~\ref{tab:schema} lists them.

\paragraph{Experimental corpus and ground truth.}
The evaluation runs on a controlled corpus where we know the ground truth
exactly, which is what makes precision and recall meaningful
(Section~\ref{sec:results}).  There are four routes: two
\emph{vulnerable} ones (\texttt{/vulnerable-pages}, \texttt{/vulnerable})
and two \emph{mitigated} ones (\texttt{/secure-pages}, \texttt{/secure}).
Each of the three users has exactly four fields that should never reach a
client: \texttt{password\_hash}, \texttt{api\_key}, \texttt{ssn}, and
\texttt{two\_factor\_secret} (a Time-based One-Time Password, or TOTP,
seed).  So a \emph{true positive} is any finding whose path ends in one of
these four fields on a user record.  Each vulnerable route holds
$4 \times 3 = 12$ planted credentials, 24 in total, and the mitigated
routes hold none.  Anything the scanner flags that is not a planted
credential is a \emph{false positive}, and any planted credential it
misses is a \emph{false negative}.  We also checked every finding in
Section~\ref{sec:results} by hand against the raw HTML, so the labels are
exact, not estimated.  Using a synthetic corpus is a deliberate choice: it
pins down the ground truth, and it avoids the legal and ethical problems of
scanning other people's production sites without permission.  We come back
to that point in Section~\ref{sec:discussion}.

\subsubsection{Vulnerability 1: Pages Router (\texttt{\_\_NEXT\_DATA\_\_})}

The page at \texttt{/vulnerable-pages} exports
\texttt{getServerSideProps}, which fetches the full user list and returns
it as the \texttt{users} prop.  The component only shows name, email, and
role.  Listing~\ref{lst:vuln_pages} shows the pattern.

\begin{lstlisting}[style=typescript, caption={Vulnerable Pages Router: raw
  database objects returned as props.}, label={lst:vuln_pages}]
// src/pages/vulnerable-pages.tsx
export const getServerSideProps: GetServerSideProps<Props> = async () => {
  const users = await getUsers(); // returns full User[] from DB

  // VULNERABILITY: raw DB objects returned directly.
  // Next.js serializes ALL fields into __NEXT_DATA__ in the HTML.
  return { props: { users } };
};
\end{lstlisting}

The resulting HTML holds the JSON in Listing~\ref{lst:next_data}.  The
bcrypt hash, the TOTP seed, the API key, and the SSN all sit there in the
page source, and any HTTP request can read them.

\begin{lstlisting}[style=json, caption={Excerpt of \_\_NEXT\_DATA\_\_ in
  the HTML response, showing leaked credentials.}, label={lst:next_data}]
<script id="__NEXT_DATA__" type="application/json">
{"props":{"pageProps":{"users":[{
  "id":1, "name":"Alice Admin", "email":"alice@example.com",
  "password_hash":"$2b$12$EixZaYVK1fsbw1ZfbX3OXe...",
  "two_factor_secret":"JBSWY3DPEHPK3PXP",
  "api_key":"sk_live_1234567890abcdef", "ssn":"000-00-0001",
  "role":"admin"}, ...]}}}
</script>
\end{lstlisting}

\subsubsection{Vulnerability 2: App Router (RSC Payload)}

The page at \texttt{/vulnerable} is a Server Component that fetches the
users and passes the raw array straight to a \texttt{'use client'} Client
Component.  Listing~\ref{lst:vuln_app} shows it.

\begin{lstlisting}[style=typescript, caption={Vulnerable App Router:
  raw objects crossing the RSC serialization boundary.},
  label={lst:vuln_app}]
// src/app/vulnerable/page.tsx
export default async function VulnerableAppRouterPage() {
  const users = await getUsers(); // full User[] from DB

  // VULNERABILITY: entire User[] passed to Client Component.
  // Next.js encodes all fields into self.__next_f.push() payloads.
  return <UserListClient users={users} />;
}
\end{lstlisting}

\texttt{UserListClient} only renders \texttt{user.name} and
\texttt{user.email}, but that does not matter.  The whole \texttt{User}
object is serialized into the RSC streaming payload in the initial HTML,
\texttt{password\_hash}, \texttt{api\_key}, \texttt{ssn},
\texttt{two\_factor\_secret} and all.

Here the data is split across a series of
\texttt{self.\_\_next\_f.push()} calls, each carrying a typed row, with row
type~1 holding the JSON-encoded parts of the component tree.  Unlike the
single \texttt{\_\_NEXT\_DATA\_\_} blob, this payload is spread over many
calls, so the scanner has to parse a newline-delimited format where each
line looks like \texttt{<row\_id>:<json\_value>}.

\subsection{Phase 2: Automated Vulnerability Scanner}

The scanner is a Python~3.12 program (\texttt{scanner.py}, about 850 lines
including the patterns, the command-line interface, and the reporting).
It uses \texttt{requests} to fetch pages and \texttt{BeautifulSoup} to
parse HTML.  Figure~\ref{fig:scanner} shows the whole flow: one HTTP GET
per target, channel extraction, a recursive walk over the recovered JSON,
two checks at each key, and a report tagged by severity.  It makes exactly
one network request per URL, so almost all of the wall-clock time is the
network, not the analysis (Section~\ref{sec:results}).

\subsubsection{Extraction Pipeline}

The scanner reads the two Next.js channels in separate ways:

\begin{enumerate}
  \item \textbf{Pages Router}: BeautifulSoup finds the
        \texttt{<script id="\_\_NEXT\_DATA\_\_">} tag and parses its
        contents as JSON.

  \item \textbf{App Router}: a compiled regular expression finds every
        \texttt{self.\_\_next\_f.push()} call in the HTML.  The scanner
        parses each payload, checks its row type, and for row type~1
        splits the payload by newline into separate JSON objects, which it
        collects for analysis.
\end{enumerate}

\subsubsection{Recursive Tree Walker}

Once it has the JSON from either channel, the scanner walks the object
graph recursively.  At every dictionary key it runs two checks.

\begin{enumerate}
  \item \textbf{Field-name matching}: the key is tested against 29
        compiled regular expressions in three severity tiers.  The
        patterns run from most specific to most general, with
        \texttt{password\_hash} before \texttt{password}, so a key that
        matches several of them gets the most descriptive label.  The
        first match wins, and a \texttt{set} of already-flagged paths
        carried through the recursion keeps the same field from being
        reported twice.

  \item \textbf{Value matching}: if a field's name did not match and its
        value is a string, the value is tested against eight format
        patterns: bcrypt hashes, Stripe-style API keys, the SSN format,
        JSON Web Tokens (JWTs), GitHub Personal Access Tokens (PATs),
        Amazon Web Services (AWS) access key IDs, Base32 strings (possible
        TOTP secrets), and 13--16-digit numbers (possible credit-card
        numbers).  The Base32 pattern requires at least sixteen characters
        (\texttt{\^{}[A-Z2-7]\{16,\}=*\$}), because real TOTP seeds are
        16--32 characters long; Section~\ref{sec:discussion} shows this
        length cutoff is what tells real secrets apart from short
        framework-internal tokens.
\end{enumerate}

The 16 CRITICAL
patterns are \texttt{password\_hash}, \texttt{hashed\_password},
\texttt{password}, \texttt{passwd}, \texttt{two\_factor\_secret},
\texttt{totp\_secret}, \texttt{otp\_secret}, \texttt{private\_key},
\texttt{api\_key}, \texttt{apikey}, \texttt{social\_security},
\texttt{ssn}, \texttt{credit\_card}, \texttt{card\_number},
\texttt{cvv}, and \texttt{secret}.  The 9 HIGH patterns cover token-like
fields (\texttt{access\_token}, \texttt{refresh\_token},
\texttt{auth\_token}, \texttt{session\_token},
\texttt{\textbackslash btoken\textbackslash b}, \texttt{jwt},
\texttt{bearer}, \texttt{encryption\_key}, \texttt{signing\_key}), and
the 5 MEDIUM patterns flag \texttt{webhook\_secret},
\texttt{internal\_id}, \texttt{is\_admin}, \texttt{admin}, and
\texttt{stripe\_customer}.

Every run is saved automatically to a \texttt{findings/} directory as a
timestamped JSON file, and a \texttt{findings/index.json} catalog records
the label, the number of targets, and the per-severity totals for each
run.  That is what makes the before/after comparison in
Section~\ref{sec:results} easy to do.

\subsection{Detection Effectiveness}
\label{sec:metrics}

To score the scanner, we take ``is this finding a real sensitive-data
exposure?'' as the ground-truth label and compute the usual metrics over
all four routes (117 findings).  Writing $\mathit{TP}$, $\mathit{FP}$, and
$\mathit{FN}$ for true positives, false positives, and false negatives:
\[
\text{Precision}=\frac{\mathit{TP}}{\mathit{TP}+\mathit{FP}},\quad
\text{Recall}=\frac{\mathit{TP}}{\mathit{TP}+\mathit{FN}},\quad
F_1=\frac{2\,\text{P}\cdot\text{R}}{\text{P}+\text{R}}.
\]
The corpus has 24 planted credentials and the scanner reports all of
them, so $\mathit{FN}=0$ and \textbf{recall is 100\%}.  For a security
detector recall is the number that matters most, because a missed
credential is a leak nobody catches.  Precision depends on what we do with
the false positives (Table~\ref{tab:metrics}).  On the raw output it is
only 20.5\% (a false-discovery rate of 79.5\%), because the Base32 value
pattern and the \texttt{className} substring match both fire on
framework-internal strings.  Looking at the CRITICAL tier alone brings
precision to 72.7\%.  Adding one allowlist of known framework-internal
field names (\texttt{className}, \texttt{style.*}, \texttt{lang},
\texttt{rel}, \texttt{parallelRouterKey}, \texttt{buildId}, \texttt{role})
drops \emph{all} of the false positives while keeping every true positive,
which gives \textbf{100\% precision at the same 100\% recall}.  So the
false positives are not a real limitation of the approach; they are a
tuning artifact, and they sit on a small, fixed set of internal keys.

\section{Mitigation: The Data Transfer Object Pattern}
\label{sec:mitigation}

\subsection{Design Rationale}

Hydration leakage comes from a missing boundary.  The server's internal
view of the data is a full database record, and it reaches the client
unchanged because nothing forces the developer to separate ``data I
fetched'' from ``data the client is allowed to see.''  There are two ways
to draw that line:

\begin{enumerate}
  \item \textbf{Blocklist (field deletion)}: After fetching, explicitly
        delete sensitive fields before returning props, e.g.,
        \texttt{delete user.password\_hash}.

  \item \textbf{Allowlist (DTO projection)}: Define a separate type
        containing only the fields permitted to cross the boundary, and
        construct instances of that type from the database records.
\end{enumerate}

The \emph{allowlist} is the right one.  A blocklist is \emph{open by
default}: add a sensitive column to the schema and it leaks to clients
until someone remembers to add it to the delete list.  An allowlist is
\emph{closed by default}: a new field simply does not exist as far as the
client is concerned until you deliberately add it to the DTO.  TypeScript
can even enforce this at compile time, so a mistake is a build error
instead of a quiet runtime leak.

\subsection{Implementation}

We define a \texttt{PublicUser} DTO in \texttt{src/lib/dto.ts} that holds
only the five fields a client should see.  Listing~\ref{lst:dto} shows it
in full.

\begin{lstlisting}[style=typescript, caption={DTO definition and
  transformation function in \texttt{src/lib/dto.ts}.},
  label={lst:dto}]
export interface PublicUser {  // password_hash, api_key, ssn,
  id: number; name: string;    // two_factor_secret: absent
  email: string; role: string; created_at: string;
}
export function toPublicUser(u: User): PublicUser {
  return { id: u.id, name: u.name, email: u.email,
           role: u.role, created_at: u.created_at };
}
export const toPublicUsers = (users: User[]): PublicUser[] =>
  users.map(toPublicUser);
\end{lstlisting}

Writing out each field in \texttt{toPublicUser} is the important part.
TypeScript's structural typing means any field left out of the returned
object is also left out of the type, so it cannot come back.  A Client
Component that takes \texttt{PublicUser[]} instead of \texttt{User[]} gets
an extra layer of safety: writing \texttt{user.password\_hash} in client
code is now a compile-time error, not a runtime leak.

Both secure routes apply the projection right at the boundary.  The Pages
Router page \texttt{/secure-pages} wraps its result with
\texttt{toPublicUsers} before returning props, and the App Router
component \texttt{/secure} does the same before it hands anything to the
Client Component:

\begin{lstlisting}[style=typescript, caption={DTO applied at both
  serialization boundaries.}, label={lst:secure}]
// Pages Router: getServerSideProps
return { props: { users: toPublicUsers(await getUsers()) } };

// App Router: server component
const publicUsers = toPublicUsers(await getUsers()); // strip first
return <SecureUserListClient users={publicUsers} />;
\end{lstlisting}

Now only the \texttt{PublicUser} shape reaches either pipeline.  The
sensitive fields are already gone before \texttt{\_\_NEXT\_DATA\_\_} or
\texttt{self.\_\_next\_f.push} encodes anything.

\section{Discussion and Limitations}
\label{sec:discussion}

\subsection{False Positives and How to Remove Them}

The scanner's raw output has false positives at both severity tiers,
listed in Table~\ref{tab:metrics}: nine CRITICAL and 84 HIGH across the
four routes.  We leave them in rather than quietly filtering them out,
which lets us pin down where they come from.  All 93 of them come from
just two things about the serialized payload.

\subsubsection{Base32 value pattern (all HIGH false positives).}
The TOTP-secret check matches any string made of Base32 characters, and
plenty of short framework-internal strings qualify: \texttt{``admin''} (a
\texttt{role} value), \texttt{``development''} (the Next.js
\texttt{buildId}), and RSC component names like \texttt{``Preload''}.
Requiring at least sixteen characters (\texttt{\^{}[A-Z2-7]\{16,\}=*\$},
about the length of a real TOTP seed) throws all of these short matches
out while still catching real 16--32-character secrets.  This is the
version we used for the cross-framework extractors
(Section~\ref{sec:crossfw}), where it produces no false positives at all.

\subsubsection{\texttt{className} substring match (all CRITICAL false positives).}
React serializes component props into the RSC payload, and
\texttt{className} is one of them.  The name \texttt{className} happens to
contain \texttt{ssn} (ignoring case), which sets off the SSN field-name
pattern.  The values are Tailwind CSS strings like \texttt{``p-8
font-sans''}, not Social Security Numbers.  These account for exactly the
five leftover CRITICAL findings on \texttt{/vulnerable} and the four on
\texttt{/secure} in Table~\ref{tab:results_comparison}.  We can remove them
by anchoring the SSN pattern to word boundaries, or, more reliably, with
the internal-field allowlist described next.

\subsubsection{Effect on precision.}
Both kinds of false positive share a useful property: they only ever show
up on a small, fixed set of framework-internal keys (\texttt{className},
\texttt{style.*}, \texttt{lang}, \texttt{rel},
\texttt{parallelRouterKey}, \texttt{buildId}, \texttt{role}), never on a
real user-data path.  As Table~\ref{tab:metrics} shows, allowlisting those
keys clears all 93 false positives without losing a single true positive,
taking precision from 20.5\% to 100\% while recall stays at 100\%.  On
user-data paths the false-positive rate is already zero: every finding on
a \texttt{users[n].*} path was a real one.  So the false positives are
just an artifact of a deliberately cautious pattern set, not a real
weakness in the approach.

\subsection{Scope and Generalizability}

This is not a Next.js-only problem, and Section~\ref{sec:crossfw} shows it
concretely: the same detection approach pulls every planted credential out
of SvelteKit's \texttt{\_\_sveltekit\_data}, Remix's
\texttt{\_\_remixContext}, and Nuxt's \texttt{\_\_NUXT\_DATA\_\_} payloads
(Table~\ref{tab:crossfw}), and the DTO mitigation does not depend on the
framework either.  Any SSR framework that serializes server-fetched data
into the HTML and passes it to client-side components can leak the same
way, including Astro in hybrid mode.

Our mock database is just a local JSON file, simpler than a real one.
Most real apps use an Object-Relational Mapper (ORM) such as
Prisma~\cite{prisma} over a relational or document database.  ORMs hand
back typed model objects that usually carry \emph{more} fields than our
small schema, so the mechanism is the same and the risk is if anything
worse: over-fetching becomes the easy default~\cite{genfer2022}.

\subsection{Developer Tooling Gap}

No standard build-time or lint-time tool warns you when a
\texttt{getServerSideProps} return value or a Server Component prop
carries fields that were never marked safe for the client.  To
TypeScript's structural type system a database-record type and a DTO type
look the same, so without nominal typing or explicit boundary annotations
the compiler lets the leak through without a word.  React's
\texttt{experimental\_taintObjectReference}~\cite{react_taint} helps on
the App Router at runtime, but it is opt-in per object and does nothing for
the Pages Router (Section~\ref{sec:toolcmp}).  What would close the gap at
write-time is a type-aware lint rule that reads the type of each value at
the server boundary and flags sensitive fields before the code ships.  We
built a proof of concept of exactly that: an ESLint rule that requires DTO
projection at \texttt{getServerSideProps} return sites and at
Server-to-Client-Component prop boundaries.  We see it as a companion to
the runtime scanner and as the most obvious next step.

\subsection{Threats to Validity}

We evaluate on controlled, synthetic corpora with fully known ground
truth on purpose.  This gives us strong \emph{internal} validity, since
precision and recall are exact rather than estimated, at some cost to
\emph{external} validity, which we address as follows.  (i)~The corpus is
small (three records, four routes), and the cross-framework fixtures are
compact representative payloads rather than captures of real running apps;
they show that detection works on each channel, while the realistic
false-positive picture comes from the full Next.js app
(Table~\ref{tab:metrics}).  (ii)~We assigned the ground-truth labels
ourselves and checked them against the raw HTML; this is mechanical for
planted credentials, but it is still a single team doing the checking.
(iii)~We do \emph{not} scan third-party production sites.  Scanning
deployed applications without permission raises legal and ethical
questions, so a proper at-scale study would need an opt-in cohort or
explicit consent; we leave that, along with turbo-stream and
partial-prerender payload formats, for future work.  None of this changes
the core result, which is mechanical: given the serialization behavior the
frameworks document, a raw record passed across the boundary \emph{is}
serialized in full.

\section{Conclusion}
\label{sec:conclusion}

Both the Pages Router and the App Router share the same hydration
mechanism, and both turn into a quiet information-disclosure bug the moment
a developer passes a raw database record as a component prop.  The
attacker needs nothing.  No special privileges, no network interception,
no browser extension.  The data is just there in the plain-text HTML of
every response, waiting to be read.

Our scanner found 24 CRITICAL credential exposures across the two routes
at 100\% recall, with no false negatives: bcrypt password hashes, live API
keys, Social Security Numbers, and TOTP two-factor seeds.  All 24 went
away once we applied the Data Transfer Object mitigation, which is 22 lines
of TypeScript, and a short internal-field allowlist pushes the scanner's
precision to 100\%.  The same bug and the same detection carry over,
essentially unchanged, to Nuxt, Remix, and SvelteKit.

Three things follow from this.

\begin{enumerate}
  \item \textbf{Use the DTO allowlist pattern everywhere.} Every value
        returned from \texttt{getServerSideProps} and every prop passed
        from a Server Component to a Client Component should go through an
        explicit DTO before it crosses the boundary.

  \item \textbf{Treat the serialized HTML payload as a public API.} If a
        field does not belong in a REST response to an anonymous caller,
        it does not belong in the hydration payload either.

  \item \textbf{Add hydration-payload review to security audits.} Today's
        scanning tools mostly look for XSS, injection, and authentication
        bypasses.  Checks against \texttt{\_\_NEXT\_DATA\_\_} and RSC push
        payloads should be part of a standard web-application assessment
        too.
\end{enumerate}

SSR frameworks are the default now, and that is not going to change.  As
they take over more of the web, the boundary between server-side data and
client-side rendering deserves the same scrutiny we have long given to API
design.  In a hydrated app, that boundary \emph{is} the API.
